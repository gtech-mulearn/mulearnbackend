# ADR-017: One layered structure for every module, with shared plumbing in `building_blocks`

Status: Accepted
Date: 2026-11-21 (first accepted 2026-11-17)
Implementation status at dev 7fd66060: not started. There is no `modules/` or `building_blocks/` package yet.

## Context

Contributors range from first-timers to maintainers. A "full" and a "thin" module variant would
force newcomers to learn two shapes and guess which applies. Cross-cutting concerns are
reimplemented per area, and a shared `utils.py` grab-bag invites business logic to leak into it.

## Options considered

- **One layered structure for every module, generated by scaffolding.**
- **Full hexagonal architecture everywhere:** too much ceremony for CRUD modules.
- **Free-form Django apps:** today's erosion.

## Decision

**Every module has the same layers and folders:**
- interface: `api/` and `tasks.py`;
- application: `services/` for writes and `selectors/` for reads;
- domain: `domain/`, with pure rules, values and errors;
- data: `data/` (models, plus a repository only where it pays) and `adapters/` (external I/O);
- `public.py` and `contracts.py`, the only surface other modules may import.

`manage.py new_module` generates the layout, and import-linter enforces it ([ADR-016](ADR-016-architecture-enforced-by-automation.md)).

**Technical capabilities shared by modules live in `building_blocks/`,** one package per
capability (`errors`, `ids`, `observability`, `api`, `auth`, `authz`, `cache`, `http`,
`messaging`, `health`, `persistence`, `config`, `flags`, `scaffolding`, `testing`):
- `building_blocks` holds no business rules and never imports `modules`;
- `errors` is framework-free, so domain code can use it;
- a module's domain layer may not import `building_blocks.persistence`, `messaging` or `http`;
- only `building_blocks.http` imports an HTTP client.

## Consequences

- There is one mental model. Some CRUD modules have nearly empty folders, an accepted cost of
  predictability.
- One implementation of each cross-cutting concern, tested once.
- A change in `building_blocks` affects every module, so it carries its own tests.

## Revisit when

- A building block grows business knowledge (move it into a module).
- A building block is needed by another service (publish it as a package).
