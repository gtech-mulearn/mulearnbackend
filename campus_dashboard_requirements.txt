0. Document Purpose & Scope
This document is the single source of truth for all backend changes required to implement the enhanced Campus Dashboard on the μLearn platform. It follows the same specification format as the Events System (ALTER 1.92) and is written for backend engineers implementing in Django REST Framework.


The Campus Dashboard is the primary management interface for Campus Leads and Enablers. It exposes analytics, student management, IG chapter management, event feeds, leaderboards, execom configuration, and social profile management for a single campus (organization of org_type='College').

1. Global Conventions
All conventions below are inherited from the existing codebase and must be followed exactly. Deviating from any convention will cause the code review to fail.


1.1 Repository Architecture
* Pattern: Feature-module Django apps — each feature area is a self-contained app under the project root.
* Existing campus app: api/v1/dashboard/campus/ (views, serializers, urls, helper files).
* New endpoints extend this same module. Do not create a separate app.
* Database models live in the db/ package, one file per domain (db/organization.py, db/task.py, db/user.py, db/event.py — new).
* No business logic in serializers beyond field-level transforms. Service logic belongs in views or dedicated helper files (_helper.py).


1.2 Authentication & Permissions
* All private endpoints use: authentication_classes = [CustomizePermission]
* Role gating uses the @role_required([RoleType.X.value, ...]) decorator.
* User ID extraction: user_id = JWTUtils.fetch_user_id(request)
* Public endpoints (readable without auth) omit the decorator but still declare authentication_classes.


1.3 Response Envelope
Every endpoint wraps its payload in CustomResponse. Never return raw JsonResponse or Response.


Success
	CustomResponse(response=data).get_success_response()
	Success + message
	CustomResponse(general_message='Done').get_success_response()
	Failure
	CustomResponse(general_message='Reason').get_failure_response()
	Validation err
	CustomResponse(message=serializer.errors).get_failure_response()
	Paginated
	CustomResponse(response={'data': s.data, 'pagination': p}).get_success_response()
	

1.4 Pagination
All list endpoints that can return more than ~20 rows must use CommonUtils.get_paginated_queryset(). The helper accepts: queryset, request, search_fields list, sort_fields dict.


paginated = CommonUtils.get_paginated_queryset(qs, request, ['full_name'], {'karma': 'wallet_user__karma'})
serializer = MySerializer(paginated['queryset'], many=True)
return CustomResponse(response={'data': serializer.data, 'pagination': paginated['pagination']}).get_success_response()

2. Database Migrations — ALTER 1.93
Two new tables are required. All existing tables referenced here (user, organization, interest_group, user_organization_link, user_role_link) remain structurally unchanged. Run ALTER 1.92 (Events System) before running 1.93.


2.1 campus_ig_chapter
Represents a campus-level chapter of a global Interest Group. A chapter is identified by the combination of org_id (campus) and ig_id (interest group). One IG can have at most one chapter per campus.


Design note: No campus_ig table existed prior to this migration. The Events System (ALTER 1.92) references campus IG pairs via (ci_org_id, ci_ig_id) columns. campus_ig_chapter is the authoritative registry that formalises which chapters exist and who leads them. ALTER 1.92 tables can optionally back-fill a campus_ig_chapter_id FK in a later migration, but this is not required for ALTER 1.93.
	

CREATE TABLE IF NOT EXISTS campus_ig_chapter
(
    id            VARCHAR(36) PRIMARY KEY NOT NULL,
    org_id        VARCHAR(36)             NOT NULL,   -- → organization.id (College)
    ig_id         VARCHAR(36)             NOT NULL,   -- → interest_group.id
    lead_user_id  VARCHAR(36),                        -- → user.id  (Campus IG Lead; NULL if vacant)
    is_active     BOOLEAN DEFAULT TRUE    NOT NULL,
    created_by    VARCHAR(36)             NOT NULL,
    created_at    DATETIME                NOT NULL,
    updated_by    VARCHAR(36)             NOT NULL,
    updated_at    DATETIME                NOT NULL,


    CONSTRAINT uq_cic_org_ig   UNIQUE (org_id, ig_id),


    CONSTRAINT fk_cic_org      FOREIGN KEY (org_id)       REFERENCES organization   (id) ON DELETE CASCADE,
    CONSTRAINT fk_cic_ig       FOREIGN KEY (ig_id)        REFERENCES interest_group (id) ON DELETE CASCADE,
    CONSTRAINT fk_cic_lead     FOREIGN KEY (lead_user_id) REFERENCES user           (id) ON DELETE SET NULL,
    CONSTRAINT fk_cic_created  FOREIGN KEY (created_by)   REFERENCES user           (id) ON DELETE RESTRICT,
    CONSTRAINT fk_cic_updated  FOREIGN KEY (updated_by)   REFERENCES user           (id) ON DELETE RESTRICT
);


-- Indexes
CREATE INDEX IF NOT EXISTS idx_cic_org    ON campus_ig_chapter (org_id);
CREATE INDEX IF NOT EXISTS idx_cic_ig     ON campus_ig_chapter (ig_id);
CREATE INDEX IF NOT EXISTS idx_cic_lead   ON campus_ig_chapter (lead_user_id);


2.2 campus_social_link
Stores social media and web presence URLs for a campus. One row per (campus, platform) pair. Allows the campus public page to display official social accounts.


CREATE TABLE IF NOT EXISTS campus_social_link
(
    id         VARCHAR(36) PRIMARY KEY NOT NULL,
    org_id     VARCHAR(36)             NOT NULL,   -- → organization.id
    platform   VARCHAR(30)             NOT NULL,   -- 'instagram','linkedin','twitter','youtube','website','facebook','github','other'
    url        VARCHAR(500)            NOT NULL,
    label      VARCHAR(100),                       -- optional display label e.g. 'Official Page'
    created_by VARCHAR(36)             NOT NULL,
    created_at DATETIME                NOT NULL,
    updated_by VARCHAR(36)             NOT NULL,
    updated_at DATETIME                NOT NULL,


    CONSTRAINT uq_csl_org_platform UNIQUE (org_id, platform),


    CONSTRAINT fk_csl_org      FOREIGN KEY (org_id)     REFERENCES organization (id) ON DELETE CASCADE,
    CONSTRAINT fk_csl_created  FOREIGN KEY (created_by) REFERENCES user         (id) ON DELETE RESTRICT,
    CONSTRAINT fk_csl_updated  FOREIGN KEY (updated_by) REFERENCES user         (id) ON DELETE RESTRICT
);


CREATE INDEX IF NOT EXISTS idx_csl_org ON campus_social_link (org_id);

5. Endpoint Specifications
5.1  GET campus-details/  (Enhanced)
Existing endpoint. Extend the CampusDetailsSerializer / CampusDetailsPublicSerializer to include the following additional fields in its response.


IMPORTANT: Do not break the existing response shape. Append new keys to the serializer output. The frontend expects all existing keys to remain.
	

New fields added to campus-details/ response
karma_rate_30d
	Total karma earned by campus students in the last 30 days (SUM from karma_activity_log).
	karma_rate_7d
	Total karma earned in the last 7 days.
	campus_ig_count
	Number of active campus_ig_chapter rows for this org.
	ig_leads
	List of {full_name, muid, profile_pic, ig_name} for all active Campus IG Leads.
	ig_chapters
	Lightweight list of {id, ig_id, ig_name, ig_cluster, lead_name, is_active} for all chapters.
	social_links
	List of {platform, url, label} — all campus_social_link rows for this org.
	

Serializer implementation notes
* karma_rate_30d: filter karma_activity_log on user__user_organization_link_user__org=org AND created_at__gte=now-30days. Aggregate SUM of karma.
* karma_rate_7d: same filter, created_at__gte=now-7days.
* campus_ig_count: CampusIGChapter.objects.filter(org=org, is_active=True).count()
* ig_leads: query users who have lead_user_id = user.id in campus_ig_chapter for this org. Join through campus_ig_chapter to get ig name.
* ig_chapters: CampusIGChapter.objects.select_related('ig','lead_user').filter(org=org)
* social_links: CampusSocialLink.objects.filter(org=org).values('platform', 'url', 'label')


Karma rate query pattern
from django.db.models import Sum
from django.utils import timezone
from db.task import KarmaActivityLog


thirty_days_ago = DateTimeUtils.get_current_utc_time() - timedelta(days=30)
karma_30d = KarmaActivityLog.objects.filter(
    user__user_organization_link_user__org=org,
    created_at__gte=thirty_days_ago
).aggregate(total=Sum('karma'))['total'] or 0


5.2  GET leaderboard/  (Enhanced)
Returns a paginated list of students ranked by karma within the campus. Existing logic in CampusStudentDetailsAPI is the base; this is a new dedicated leaderboard endpoint that is publicly accessible.

	perPage

	cluster
	Filter to students in IGs belonging to this cluster
	search
	Substring match on full_name or muid
	sortBy
	Field to sort by: karma (desc default), full_name, join_date
	

Response shape (each item)

	Integer rank on this campus (computed from overall karma ordering before pagination)
	user_id
	UUID
	full_name
	string
	muid
	string
	profile_pic
	URL or null
	karma
	integer — wallet.karma
	level
	string — level.name from user_lvl_link
	join_date
	ISO datetime — user_organization_link.created_at
	last_karma_at
	ISO datetime — wallet.karma_last_updated_at
	graduation_year
	string or null
	department
	string or null
	is_alumni
	boolean
	ig_count
	integer — number of IGs the user is a member of
	

Implementation pattern
# 1. Build base queryset (all students in campus)
qs = User.objects.filter(
    user_organization_link_user__org=org,
    user_organization_link_user__org__org_type=OrganizationType.COLLEGE.value,
).distinct()


# 2. Apply optional filters
if pass_out_year: qs = qs.filter(user_organization_link_user__graduation_year=pass_out_year)
if ig_id:         qs = qs.filter(user_ig_link_user__ig_id=ig_id)
if cluster:       qs = qs.filter(user_ig_link_user__ig__cluster=cluster)
if is_alumni:     qs = qs.filter(user_organization_link_user__is_alumni=is_alumni)


# 3. Compute global rank dict BEFORE pagination (on full karma-sorted set)
rank_qs = Wallet.objects.filter(
    user__user_organization_link_user__org=org,
).distinct().order_by('-karma', 'created_at').values('user_id')
ranks = {r['user_id']: i + 1 for i, r in enumerate(rank_qs)}


# 4. Annotate and paginate
qs = qs.annotate(karma=F('wallet_user__karma'), ...)
paginated = CommonUtils.get_paginated_queryset(qs, request, ['full_name', 'muid'], {...})

5.6  GET / POST / DELETE execom/
Manages the campus execom — the set of users with specific operational roles in the campus. This includes Campus Lead, Lead Enabler, and all Campus IG Lead roles.


GET execom/
Returns all users currently holding roles associated with this campus.


Response
	List of { user_id, full_name, muid, profile_pic, role, ig_name (if IG role) }
	Auth
	Campus Lead or Enabler
	Logic
	Query user_role_link WHERE user is a member of this org. Join role table for role title.
	

POST execom/  (add execom member)
Assigns a campus role to an existing campus member. The user must already be in user_organization_link for this org.


Body: user_muid
	MUID of the student to appoint — must be a current campus member
	Body: role_title
	Role title string from the role table (e.g. 'LeadEnabler', or a CampusIGLead role)
	Validation
	Verify user is in user_organization_link for this org. Verify role exists. Check not already assigned.
	Side effect
	Create UserRoleLink record. If role is a CampusIG role, also upsert campus_ig_chapter.lead_user_id.
	Auth
	Campus Lead only (CAMPUS_LEAD role)
	

DELETE execom/<member_id>/
Removes an execom role from a user. member_id is the user_role_link.id.


Auth
	Campus Lead only
	Restriction
	Cannot remove the current Campus Lead's own lead role. Cannot remove an admin.
	Side effect
	Delete UserRoleLink row. If it was a CampusIG role, clear campus_ig_chapter.lead_user_id.
	

5.7  Campus IG Chapters CRUD  ( ig-chapters/ )


GET ig-chapters/
Returns all campus_ig_chapter rows for this campus with lead and IG details.


Auth
	Campus Lead or Enabler
	Query
	CampusIGChapter.objects.select_related('ig','lead_user').filter(org=org)
	Response
	List of { id, ig: {id, name, cluster, icon}, lead: {user_id, full_name, muid} | null, is_active, member_count, created_at }
	member_count
	Count of user_ig_link rows where ig_id matches AND user is in this campus — computed via annotation.
	

POST ig-chapters/  (create chapter)
Creates a new campus IG chapter. The IG must be a globally approved interest_group. Only one chapter per IG per campus is allowed (enforced by unique constraint).


Body: ig_id
	UUID of the global interest_group to create a chapter of
	Body: lead_user_muid
	Optional — MUID of the student to appoint as Campus IG Lead immediately
	Validation
	interest_group must exist. user must be a campus member if provided. Chapter must not already exist (unique constraint).
	Side effect
	Insert campus_ig_chapter. If lead_user_muid provided: upsert UserRoleLink for the IG's lead role (title: ig.code + 'CampusLead'). Update chapter.lead_user_id.
	Auth
	Campus Lead or Enabler
	Returns
	Newly created chapter object
	

PATCH ig-chapters/<chapter_id>/  (update chapter)
Partially update a chapter. The primary use case is re-assigning the Campus IG Lead (replicates the existing TransferIGRoleAPI logic, but tied to a specific chapter).


Body: lead_user_muid
	MUID of new lead — must be a campus member
	Body: is_active
	boolean — to activate or deactivate the chapter
	Side effect on lead change
	Remove old UserRoleLink for IG lead role. Create new UserRoleLink for the new user. Update campus_ig_chapter.lead_user_id.
	Auth
	Campus Lead or Enabler
	

DELETE ig-chapters/<chapter_id>/
Soft deactivates a chapter by setting is_active=False. Does not hard-delete the record.


Auth
	Campus Lead only
	Side effect
	Set is_active=False. Clear lead_user_id. Remove associated CampusIG Lead UserRoleLink.

10. Performance Considerations


10.1 N+1 Query Prevention
* Always use select_related() for single ForeignKey traversals in list endpoints.
* Use prefetch_related() for reverse relations and M2M in list endpoints.
* Compute rank dict via a single wallet queryset before serialization — do not query wallet per user inside the serializer.
* Annotate computed fields (karma, level name, ig_count) on the queryset in the view, not inside SerializerMethodField loops.


10.2 Index Reliance
* karma-by-cluster query relies on user_ig_link.ig_id (already indexed via FK) and interest_group.cluster (indexed in ALTER 1.92 as idx_ig_cluster).
* campus events query relies on event_scope.target_org_id (indexed as idx_es_campus in ALTER 1.92).
* campus_ig_chapter lookups rely on idx_cic_org added in ALTER 1.93.
* campus_social_link lookups rely on idx_csl_org added in ALTER 1.93.


10.3 Leaderboard Rank Computation
Computing a global rank for a paginated list requires materialising the full sorted wallet queryset before slicing. This is acceptable given campus sizes (typically < 5,000 students) but should be revisited if campuses exceed 20,000 members. At that scale, store rank in a nightly-computed cache column.
Use .values('user_id') on the rank queryset to avoid fetching full User objects — only IDs are needed for the rank dict.

def validate_campus_member(user_id, org):
    '''
    Returns True if the given user_id has a UserOrganizationLink
    for this org with org_type=COLLEGE. False otherwise.
    '''
    return UserOrganizationLink.objects.filter(

def get_campus_ig_chapter(chapter_id, org):
    '''
    Returns CampusIGChapter if it belongs to org, else None.
    Always scope by org to prevent cross-campus access.
    '''
    return CampusIGChapter.objects.filter(id=chapter_id, org=org).first()


assign_ig_lead_role(user, ig, org, created_by_id)
def assign_ig_lead_role(user, ig, org, created_by_id):
    '''
    Upserts a UserRoleLink for the IG Lead role (title = ig.code + 'CampusLead').
    Removes any existing holder of that role in this campus first.
    Mirrors the logic in TransferIGRoleAPI.
    '''
    role = Role.objects.filter(title=f'{ig.code}CampusLead').first()
    if role is None:
        return None, 'IG lead role not found'
    # Remove old lead
    UserRoleLink.objects.filter(
        user__user_organization_link_user__org=org,
        role=role
    ).delete()
    # Assign new lead
    UserRoleLink.objects.create(
        id=str(uuid.uuid4()), user=user, role=role,
        verified=True, created_by_id=created_by_id, created_at=DateTimeUtils.get_current_utc_time()
    )
    return role, None

14. Key Design Decisions


1. campus_ig_chapter as the IG Chapter Registry
Prior to this migration, campus IG chapters were implied by the co-existence of user_organization_link and user_ig_link rows, with the Campus IG Lead role stored as a UserRoleLink with a title of '{ig.code}CampusLead'. This worked for role assignment but provided no single place to query 'which IG chapters exist at this campus'. campus_ig_chapter formalises this as a first-class entity, enabling: member counts per chapter, chapter active/inactive states, clean API for creating/deactivating chapters, and a direct FK for the ALTER 1.92 event tables to reference.


2. Upsert semantics for Social Links
Since platform is unique per campus, POST social-links/ always upserts. This simplifies the frontend — it doesn't need to track whether a social link exists before deciding POST vs PATCH. The backend uses update_or_create() transparently.


3. Rank computed before pagination
The leaderboard rank is a positional rank (1st, 2nd, 3rd...) within the campus, not a score. It must be computed across the full student set before pagination slices it. The pattern is: materialise the full karma-sorted wallet queryset as a dict, then paginate the main student queryset. The rank dict lookup is O(1) per student in the page. This matches the pattern already used in the existing CampusStudentDetailsAPI.


4. Events from ALTER 1.92 — read-only access
The Campus Dashboard reads events from the ALTER 1.92 tables but does not create or manage them through this module. Event creation for campus leads is handled by the Events API module (POST /manage/events/). The campus endpoints only read event data for display in the campus-specific events tab and analytics charts.


5. Public endpoints scoped by org_id query param
Social links and the public campus detail are accessible without authentication. Instead of using the authenticated user's campus, these endpoints accept an org_id as a URL path parameter or query param. The existing GET <org_id>/ endpoint already follows this pattern.
